# 工具调用：封号风险评估与设计约束

> 写于实现之前。依据：`dsh-deepseek-web-login` 的实测记录（四个账号两天内被限制）
> + `cuckoo-code` 的做法（从未被风控）。

## 一、参考实现记录的封号触发条件（原文证据）

| 触发条件 | 原文 | 出处 |
|---|---|---|
| **并发生成** | 「网页端同一账号**同时只能生成一条**…双窗口并发生成不到 6 分钟就触发账号级限制（mute 1 天）」 | `index.js:881-883` |
| **单次请求体量** | 「会话内实测单次输入从 9.7k token 一路涨到 **293k**…四个账号两天内陆续被限制，体量是主要嫌疑」 | `index.js:934-936` |
| **请求密度** | 「固定间隔的方差≈0，在统计上就是『定时器特征』；人的操作间隔是有方差的」 | `index.js:893-894` |
| **设备指纹缺失** | 「上游对『缺少浏览器设备指纹』会直接返回 `biz_code=11 / RISK_DEVICE_DETECTED`」 | `index.js:622-623` |

## 二、本插件现状（三道防线已就位）

| 防线 | 本插件做法 | 对应风险 |
|---|---|---|
| **串行** | `busy` + `pendingJobRef` 闸门，一次只跑一个任务 | 并发 → mute 1 天 |
| **差分发送** | 只发增量，不重发历史 | 体量 → 293k token |
| **随机间隔** | `pickSendDelay()` 2000~4000ms | 定时器特征 |

**关键优势**：本插件用**真实浏览器**发请求，TLS/HTTP2/PoW/cookie/`x-device-id`
全部天然正确 —— 参考实现最头疼的「设备指纹缺失」（`RISK_DEVICE_DETECTED`）
在本插件里**根本不存在**。

## 三、工具调用引入的**新**风险

### 风险 1：工具目录撑大 prompt（高）

DSH 下发 **61 个工具**，完整描述约 **50,942 字符**（参考实现实测）。
若每轮都带上，首轮 prompt 就从「一条用户消息」暴涨到 5 万+ 字符。

**这直接撞上参考实现记录的体量红线。**

**规避**：分级下发（抄参考实现的 `CORE_TOOLS` 白名单）

| 级别 | 工具 | 描述长度 |
|---|---|---|
| 核心 | `pwsh` `read` `write` `edit` `grep` `glob` `bash` `run_code` `todo_write` `skill` `present` `ask_user_question` | 完整（≤3200 字符） |
| 长尾 | 其余 ~49 个 | **一行**（`name(签名)` — 首句，≤160 字符） |

依据：参考实现扫 826 次真实调用，核心 13 个覆盖 **90%**。
长尾工具仍**可被调用**（名字+签名都在），只是看不到长篇说明。

### 风险 2：工具结果回灌进网页对话（高）

参考实现把工具结果序列化成 `[Tool Result for xxx]` 文本发回网页 ——
**这会永久留在网页端聊天记录里**，每轮重发，越滚越大。

**规避**：本插件已有**差分发送**，工具结果作为「新增消息」只发一次，
不重发历史。但要注意：**工具结果本身可能很大**（比���读一个 10KB 文件）。

**对策**：单条工具结果超过阈值时截断（带明确标记），
避免一次读文件就把 prompt 顶到红线。

### 风险 3：`dsh-tool` 围栏泄漏到可见记录（中）

参考实现 rule 6 专门警告：「An unfenced object or any such markup
**leaks into the visible transcript and into the web conversation**」。

模型偶尔会把 JSON 写成正文（不带围栏），或写成 XML 风格标记。
那些垃圾会留在网页端记录里，看起来极不像人。

**规避**：hold-back 扫描器必须**同时处理三种形态**：
围栏 JSON、裸 JSON、XML 风格标记（`<tool_calls>` / `<invoke>` / DSML）。
命中即捕获转成 tool-call 块，**绝不透传到正文**。

### 风险 4：协议指令本身占上下文（低）

`TOOL_PROTOCOL_INSTRUCTIONS` 约 2,000 字符。它是固定前缀，
参考实现特意说明「进 prompt 前缀，保持前缀缓存友好」——
但本插件走真实浏览器，**没有前缀缓存**（页面自己发请求）。

**对策**：只在**首轮**（`isFirst`）附带协议指令，后续轮次不重复 ——
正好与差分发送一致（首轮发 system + 协议，之后只发增量）。

### 风险 5：工具循环导致请求密度上升（中）

一个 agent 任务可能连续调 10 次工具 = 10 轮请求。
参考实现有 `minIntervalMs`（2~4 秒）和**长休**（每 N 次休息 1~3 分钟）。

**本插件现状**：`pickSendDelay()` 已有 2~4 秒随机。
**缺口**：没有长休机制。连续 20+ 轮工具调用时，请求密度会很高。

**对策**：加**长休**（连续 N 次请求后随机休息 1~3 分钟），
阈值可配置，默认保守。

## 四、实现顺序（每步都可独立验证）

1. **工具目录下发**（分级 + 预算控制）→ 测试：prompt 长度不超预算
2. **协议指令**（仅首轮）→ 测试：首轮含协议、后续轮不含
3. **消息序列化**（tool-call / tool-result 两种块的文本化）→ 测试：往返正确
4. **hold-back 扫描器**（流式捕获 + 三形态）→ 测试：用真实帧序列
5. **tool-call chunk 发射**（block-start / delta / block-end）→ 测试：chunk 契约
6. **长休机制**（请求密度阀门）→ 测试：阈值触发

## 五、验收标准

- 工具调用能真的执行（DSH 收到合法 `tool-call` chunk）
- 工具结果能回到模型（下一轮增量里带上）
- **首轮 prompt 长度 < 6 万字符**（工具目录 + 协议 + system + 首条消息）
- 后续轮 prompt 只含增量（不含工具目录、不含协议）
- 连续请求有长休，密度不超过参考实现
